# CLAUDE.md — постоянные правила проекта

Этот файл описывает правила, которые действуют на всех этапах работы над проектом
и не пересматриваются без явного решения пользователя. Полное ТЗ — в
[docs/SPEC.md](docs/SPEC.md), архитектура — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md),
план этапов — в [docs/PLAN.md](docs/PLAN.md), текущий статус — в [CURRENT_STATE.md](CURRENT_STATE.md).

## О проекте

Desktop-приложение для автоматического заполнения электронного журнала
спортивных тренировок. Конечный пользователь — тренер или администратор без
навыков программирования. Ему не должны требоваться Python, VS Code,
терминал или редактирование файлов настроек.

## Технологический стек (предварительный)

Python, PySide6, Playwright, SQLite, YAML (импорт/экспорт настроек), pytest,
Python logging, PyInstaller (сборка под Windows). Конкретные версии
фиксируются в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) после проверки
совместимости, а не выбираются произвольно на ходу.

## Постоянные архитектурные и продуктовые правила

1. Разделять интерфейс, планировщик, бизнес-логику, хранение данных и адаптер
   сайта — как отдельные слои/модули, не смешивать их ответственность.
2. Не блокировать интерфейс браузерными операциями и ожиданием. Вся работа с
   Playwright и ожидание времени запуска выполняются вне потока GUI.
3. Не заполнять журнал до начала занятия. Поддерживать запуск со смещением
   после начала или после окончания занятия (по умолчанию — через 10 минут
   после окончания).
4. Часовой пояс всегда задаётся явно, по умолчанию `Europe/Moscow`.
5. Отмечать остальных спортсменов присутствующими можно только после
   подтверждения, что список отсутствующих для конкретного занятия полный.
   «Пустой подтверждённый список» и «данных о посещаемости нет» — разные
   состояния, их нельзя путать.
6. Не придумывать причины отсутствия и не выбирать их случайно. Используются
   только шаблоны или текст, явно переданные пользователем.
7. Использовать только реальные фотографии соответствующей тренировки. Не
   изменять метаданные фотографии ради совпадения с расписанием и не
   подставлять фото с другого занятия.
8. Недостаток данных по одному занятию (нет фото, нет посещаемости, нет
   причины) не должен блокировать обработку других, независимых занятий.
9. С самого начала проектировать защиту от дублей, от частично выполненных
   действий и от неизвестного результата сохранения. Нажатие кнопки —
   не доказательство успешного сохранения; результат нужно проверять.
10. Проверочный (dry-run) режим не должен изменять журнал ни в каком виде,
    включая загрузку фото и поля с автосохранением.
11. До изучения реального сайта использовать демонстрационный (demo) адаптер.
    Не выдумывать реальные селекторы, адреса страниц или особенности
    интерфейса сайта — только то, что подтверждено скриншотами/описанием
    пользователя.
12. Секреты конечного пользователя (логин/пароль от журнала) хранить через
    системное хранилище учётных данных ОС. `.env` допустим только при
    локальной разработке и никогда не коммитится (см. `.gitignore`).
13. Данные пользователя (БД, фотографии, реальные списки спортсменов, логи)
    хранятся отдельно от каталога установленной программы.
14. Локальная автоматизация работает, только пока приложение запущено, а
    компьютер включён, не спит и подключён к интернету — это ограничение
    нужно явно показывать пользователю в интерфейсе, а не скрывать.
15. Любые реальные изменения в журнале в процессе разработки выполняются
    только на явно согласованном с пользователем занятии или в тестовой
    среде — никогда «по умолчанию» на реальных данных без подтверждения.

## Правила работы с Git и GitHub

- Репозиторий: `https://github.com/kuzikovadara58-glitch/my-project.git`.
  Пользователь разрешил создавать commits и выполнять обычный push в этот
  репозиторий без повторного согласования каждого раза.
- Основная ветка — `main` (репозиторий не был пустым: перед началом работы
  существующие `README.md` и `.gitignore` были изучены и объединены с
  проектом, ничего не удалялось вслепую).
- Если прямой push в `main` окажется запрещён политикой репозитория —
  использовать рабочую ветку и явно сообщить об этом пользователю, не
  пытаться обойти защиту веток.
- Никогда не использовать force push, не переписывать опубликованную
  историю.
- После каждого небольшого законченного и проверенного набора изменений:
  проверить diff → добавить только относящиеся к задаче файлы → сделать
  commit с понятным сообщением → push → проверить, что push действительно
  дошёл до GitHub. Не копить все commits до конца этапа, но и не коммитить
  после каждого отдельного сохранения файла.
- Секреты никогда не попадают в remote URL, в код или в коммиты. Если для
  push нет авторизации — объяснить пользователю локальный способ входа
  (например, `gh auth login` или Git Credential Manager), не запрашивая
  пароль или токен в чате.
- Если push недоступен — продолжать работу локальными коммитами, явно
  сообщать, что именно ещё не отправлено на GitHub, и выполнить push, как
  только авторизация появится. Локальный commit никогда не выдаётся за
  успешную отправку на GitHub.
- До первого commit в проекте должен существовать `.gitignore`, исключающий
  реальные `.env`, пароли, токены, сессии браузера, пользовательские базы,
  фотографии детей, реальные списки спортсменов, логи и диагностические
  снимки, виртуальное окружение и сборочные артефакты. Примеры в репозитории
  содержат только вымышленные данные.

## Дисциплина документации на каждом этапе

- Перед началом работы над этапом — прочитать `docs/SPEC.md`,
  `docs/ARCHITECTURE.md`, `docs/PLAN.md`, `CURRENT_STATE.md`.
- После завершения этапа — обновить `CURRENT_STATE.md` и, если нужно,
  `docs/ARCHITECTURE.md`/`docs/PLAN.md`.
- Если ожидаемый файл документации отсутствует — восстановить его из
  доступных требований (этого файла, SPEC.md, истории репозитория), явно
  указав, что он был восстановлен, а не «прочитан как есть».
- В конце каждого этапа сообщать пользователю: что готово; как проверено;
  что осталось; ветку и хеш последнего отправленного commit — либо причину,
  по которой push не выполнен.
