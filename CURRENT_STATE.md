## Что готово

- `journal_automation/scheduler/timing.py`: расчёт момента заполнения
  занятия (`compute_fill_time`) — учитывает `fill_after_start_minutes`/
  `fill_after_end_minutes` из настроек этапа 2.
- `journal_automation/scheduler/core.py`: `SchedulerLoop` — планировщик без
  зависимости от Qt, ожидание через `threading.Event.wait()` (без занятого
  цикла), обработка занятий по одному с изоляцией ошибок, защита от
  штормового авто-повтора `ERROR`/`NEEDS_ATTENTION` в рамках одного запуска.
- `journal_automation/scheduler/controller.py`: `AutomationController`
  (`QThread`) — GUI не блокируется, обмен только через Qt-сигналы, повторный
  клик «Запустить» не создаёт второй планировщик, остановка кооперативная,
  `shutdown()` для закрытия приложения без зависших потоков.
- `journal_automation/automation/`: `JournalAutomationPort` (интерфейс) и
  `MockJournalAutomation` — безопасная имитация обработки занятия
  (PENDING → WAITING → RUNNING → SUCCESS/ERROR), поддержка
  `--simulate-error`, реальный сайт не затрагивается.
- `journal_automation/gui/main_window.py` + `main.py`: desktop-окно на
  PySide6 — сегодняшние занятия, обе оси состояния, кнопки «Запустить»/
  «Остановить», «Последнее событие», минимальный просмотр настроек.
- `journal_automation/demo.py`: изолированный демо-режим
  (`python main.py --demo`) на временных данных, не трогает config/ и
  реальную историю пользователя; занятия наступают через секунды.
- `journal_automation/logging_setup.py`: логирование в файл и консоль без
  паролей/фото/лишних персональных данных.
- `HistoryManager` защищён `threading.Lock` — с этого этапа к нему
  обращаются GUI-поток и поток планировщика одновременно (доработка
  `journal_automation/services/history_manager.py`).
- `journal_automation/app.py`: `AppContext`/`build_app_context` — общая
  сборка слоёв для CLI-демо (`scripts/demo_today.py`, обновлён под новый
  API) и desktop-приложения.

## Как проверено

- `pytest -q` — **65 тестов**, все проходят (48 из этапа 2 + 17 новых):
  расчёт времени заполнения, `SchedulerLoop` (нормальная обработка, пустое
  расписание, `SUCCESS` не переобрабатывается, `ERROR` не запускается по
  кругу в рамках одного запуска, остановка во время ожидания не запускает
  обработку, кооперативная отмена не пишет в историю), `MockJournalAutomation`
  (SUCCESS/ERROR-сценарии, отмена по `stop_event`, тесты быстрые — без
  реального ожидания минут), `AutomationController` (обработка сигналов,
  двойной клик не создаёт второй планировщик, `stop`/`shutdown` останавливают
  поток), сквозной сценарий "перезапуск программы после SUCCESS"
  (`tests/test_duplicate_protection.py`, раздел 19 запроса пользователя).
- Ручная/автоматизированная проверка `python main.py --demo` (и
  `--simulate-error`) через `QT_QPA_PLATFORM=offscreen`, поскольку в среде
  разработки нет интерактивного дисплея: окно открывается, оба демо-занятия
  проходят WAITING → RUNNING → SUCCESS (или ERROR), второй клик «Запустить»
  не создаёт второй планировщик, «Остановить» останавливает без обработки
  ожидающего занятия, закрытие окна не оставляет работающий поток
  (`controller.isRunning()` — `False` после `shutdown()`), в истории —
  верные записи для обоих занятий по отдельности (после исправления
  найденного при проверке бага — см. ниже).
- `python main.py` (без `--demo`) и `python main.py --simulate-error` (без
  `--demo`) — оба пройдены: обычный режим стартует на реальном `config/`
  (сегодня по реальному календарю тренировок нет — корректный пустой
  список), а `--simulate-error` без `--demo` корректно отклоняется
  `argparse` с понятной ошибкой.

## Найден и исправлен баг

При ручной проверке demo-режима оба демо-занятия изначально получали
**одинаковый `session_id`**: формат `session_id` — `ГГГГ-ММ-ДД:group_id:ЧЧ:ММ`
(точность до минуты, корректно для реального расписания, этап 2) — а два
демо-занятия были разнесены всего на 10 секунд, то есть попадали в одну и ту
же минуту. Второе занятие в результате считалось тем же самым, уже
успешно обработанным. Исправлено увеличением интервала между демо-занятиями
до заведомо больше 60 секунд (`journal_automation/demo.py`) — гарантированно
переходит границу минуты при любом старте. Формат `session_id` из этапа 2
не менялся (он корректен для реальных данных).
