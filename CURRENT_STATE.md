# CURRENT_STATE.md — текущее состояние проекта

## Этап

**4. Google Drive Photo Source** — завершён (см. docs/PLAN.md; пользователь
направил этот номер этапа на получение фото из Google Drive — исходно
запланированный на этом месте расширенный GUI-редактор конфигурации
перенесён в docs/PLAN.md как отдельный пункт без номера).

## Что готово

- Пакет `journal_automation/photos/`: `PhotoSource` (Protocol),
  `PhotoService` (оркестратор выбора фото), `GoogleDrivePhotoSource`
  (реальный Google Drive API v3 — не Playwright, не парсинг HTML),
  `FakeGoogleDrivePhotoSource` (demo), `google_drive_auth.py` (OAuth
  "installed app" flow), `google_drive_url.py` (разбор ссылки на папку),
  `exif_reader.py` (Pillow), `filename_parser.py`, `validation.py`
  (`is_photo_time_valid`), `cache.py` (`PhotoCache`), `presentation.py`
  (единый текст статуса для GUI и логов), `models.py` (`TrainingPhoto`,
  `PhotoSelectionStatus`).
- Конфигурация: новая секция `photos:` в `settings.yaml`
  (`PhotosSettings`/`GoogleDriveSettings` в
  `journal_automation/config/models.py`, парсинг и валидация ссылки в
  `ConfigManager`) — опциональна, отсутствие не ломает старые конфиги
  (используются значения по умолчанию), задокументировано отличие от
  задела этапа 2 (`AutomationSettings.photo_time_tolerance_*` остаются
  нетронутыми, но не используются новым конвейером — см.
  `docs/ARCHITECTURE.md` §6).
- `SchedulerLoop` перед вызовом автоматизации опционально (только если
  передан `photo_service`) проверяет фото: `FOUND` → передаёт фото в
  `JournalAutomationPort.process_session(session, stop_event, photo)`
  (новый необязательный параметр, по умолчанию `None` — обратная
  совместимость с этапом 3); `WAITING_FOR_PHOTO` → пауза
  `recheck_interval_seconds` и повтор, не считается попыткой обработки;
  остальное → `NEEDS_ATTENTION` в истории.
- Защита от «скачать всю папку»: `PhotoService` сначала получает только
  метаданные, дёшево отсеивает по имени файла кандидатов с явно другой
  датой без скачивания, скачивает не больше `_MAX_CANDIDATES_TO_DOWNLOAD`
  (по умолчанию 5) реально отобранных.
- Приоритет времени съёмки: EXIF → имя файла → (только если явно разрешено
  `photos.allow_drive_timestamp_fallback`, по умолчанию `false`) метаданные
  Google Drive. Ничего не подделывается ради совпадения.
- Детерминированный выбор при нескольких валидных кандидатах; настоящая
  неоднозначность (одинаковое время съёмки и источник) → `AMBIGUOUS`, не
  случайный выбор.
- Retry с backoff для временных ошибок Google Drive (429/5xx/сеть), без
  повтора для permission denied; отдельно различены «источник недоступен
  целиком» и «один файл исчез между list и download» (последнее не
  прерывает поиск).
- Локальный кэш скачанных фото (`data/cache/photos/` под пользовательским
  каталогом данных) с повторным использованием без повторного скачивания и
  очисткой по `cache_retention_days` (не трогает файлы, которые сейчас
  используются, и никогда не трогает сам Google Drive).
- GUI: построчный статус «Фото: ...» и кнопка «🔄 Проверить фото» на каждое
  занятие (`PhotoCheckWorker` — отдельный `QThread`, не блокирует
  интерфейс); просмотр настроек дополнен источником фото и папкой Drive.
- Demo-режим (`--demo`) не обращается к реальному Google Drive
  (`FakeGoogleDrivePhotoSource`, настоящий JPEG с настоящим EXIF через
  Pillow — тот же код чтения EXIF, что и с реальным Drive). Новые флаги:
  `--simulate-photo-missing`, `--simulate-drive-error`,
  `--simulate-photo-ambiguous` (взаимоисключающие, требуют `--demo`).

## Как проверено

- `pytest -q` — **118 тестов** (65 из этапов 2-3 + 53 новых), 1 тест
  помечен `google_drive` и по умолчанию не запускается (`pytest.ini`:
  `addopts = -m "not google_drive"`; запуск вручную — `pytest -m google_drive`,
  без реальных credentials корректно пропускается). Покрыто: разбор ссылки
  Google Drive, `GoogleDrivePhotoSource` (список файлов, пустая папка,
  permission denied, временная ошибка с retry, скачивание, файл исчез между
  list/download — всё на дублёре API, без интернета), EXIF (есть/нет/битый),
  парсер имени файла, `is_photo_time_valid`/`validate_training_photo`
  (верная/неверная дата, валидное/слишком раннее/слишком позднее время),
  `PhotoService` (один кандидат, несколько кандидатов, приоритет EXIF над
  именем файла при равном расстоянии, настоящая неоднозначность, кандидат
  пропал при скачивании — не фатально, ограничение числа скачиваний,
  drive-timestamp fallback выключен/включён), кэш (детерминированный путь,
  переиспользование, очистка старых файлов с защитой используемых).
- Автоматизированная проверка всех четырёх demo-сценариев через реальные
  `MainWindow`/`AutomationController`/`SchedulerLoop`
  (`QT_QPA_PLATFORM=offscreen`, т.к. в среде разработки нет интерактивного
  дисплея): `success` → фото найдено → `SUCCESS`; `missing` → `WAITING_FOR_PHOTO`
  → после дедлайна `NEEDS_ATTENTION`; `error` → `SOURCE_UNAVAILABLE` →
  `NEEDS_ATTENTION`, GUI не падает; `ambiguous` → `AMBIGUOUS` →
  `NEEDS_ATTENTION`. Проверены и реальные CLI-ограничения `main.py`
  (`--simulate-*` требуют `--demo`, взаимоисключающие).
- `python main.py` (без `--demo`) по-прежнему стартует на реальном
  `config/` — с плейсхолдером `folder_url: ""` источник фото отключён,
  поведение идентично этапу 3 (проверено вручную).

## Найдены и исправлены баги (при ручной проверке, до передачи в тесты)

- `PhotoCache.path_for` не санитизировал `remote_file_id` — demo-источник
  подставлял туда `session_id` с двоеточиями, недопустимыми в путях Windows
  (`OSError: Invalid argument`). Исправлено: `remote_file_id` теперь тоже
  проходит через ту же санитизацию, что и `remote_name`.
- Demo-сценарий `ambiguous` изначально называл второй файл с суффиксом
  `_alt`, из-за чего анкорованный парсер имени файла переставал его
  распознавать — кандидат считался невалидным (нет времени съёмки), а не
  честно неоднозначным. Исправлено: второй демо-файл называется идентично
  первому (в Google Drive два файла в одной папке действительно могут
  называться одинаково), что и вызывает настоящую неоднозначность.
