# PLAN.md — план разработки по этапам

Восемь этапов. Каждый этап заканчивается коммитом/push и отчётом по схеме:
что готово / как проверено / что осталось / ветка и последний commit.
Реальные изменения в журнале в процессе разработки — только на явно
согласованном с пользователем занятии или в тестовой среде.

## Этап 1. Архитектура (текущий)

**Цель:** зафиксировать архитектуру, сущности, состояния и правила проекта,
не реализуя приложение целиком.

Результат:
- `CLAUDE.md`, `docs/SPEC.md`, `docs/ARCHITECTURE.md`, `docs/PLAN.md`,
  `CURRENT_STATE.md`, `README.md`, `.gitignore`.
- Git подключён к `https://github.com/kuzikovadara58-glitch/my-project.git`,
  ветка `main`.

Как проверено: документы вычитаны на непротиворечивость друг другу и ТЗ;
код не писался, поэтому автоматических тестов на этом этапе нет.

## Этап 2. Данные — ВЫПОЛНЕНО

**Цель:** слой хранения и конфигурации, независимый от GUI и планировщика.

- Зафиксированы версии стека в `requirements.txt` (Python 3.11+, проверено
  на 3.14.6; PySide6, Playwright, PyYAML, python-dotenv, pytest, keyring,
  platformdirs, tzdata) — установлены совместно в чистое окружение, тесты
  прошли. PyInstaller добавится на этапе «Сборка».
- **Отличие от первоначального плана**, зафиксированное здесь, а не молча:
  вместо схемы SQLite для группы/спортсменов/расписания/посещаемости —
  типизированные модели (`journal_automation/config/models.py`), читаемые
  и валидируемые из YAML через `ConfigManager`
  (`journal_automation/config/manager.py`); история выполнения занятий —
  один JSON-файл через `HistoryManager`
  (`journal_automation/services/history_manager.py`), а не таблица SQLite.
  Переход на SQLite откладывается до момента, когда он реально понадобится —
  конкурентный доступ планировщика (этап 3) и GUI (этап 4) к одним и тем же
  данным; до тех пор SQLite был бы неиспользуемой инфраструктурой. Причины
  и последствия — в `docs/ARCHITECTURE.md`, раздел 6.
- Модуль секретов через `keyring` с `.env`-фолбэком только для разработки
  (`journal_automation/secrets.py`), включается явно
  `JOURNAL_ALLOW_DOTENV_SECRETS=1`.
- Единая точка разрешения путей `journal_automation/paths.py` (`AppPaths`):
  каталог пользовательских данных отдельно от каталога с конфигурацией и от
  каталога программы, учитывает будущую сборку в `.exe`.
- Обе оси состояния занятия из `ARCHITECTURE.md` §4 реализованы как
  `TrainingDomainState` и `AutomationState`
  (`journal_automation/domain/states.py`), с таблицей соответствия
  русскоязычному жизненному циклу этапа 1.
- Защита от повторной обработки (`TrainingService.should_process_session`)
  и от перепутывания причины отсутствия между спортсменами
  (`journal_automation/domain/absence.py`, сопоставление по `athlete_id`).
- Доменная модель и проверки фотографии
  (`journal_automation/domain/photo.py`): формат/размер, дубли по хешу
  файла, окно допуска по времени съёмки. Чтение EXIF из реального файла —
  открытый вопрос (см. `docs/ARCHITECTURE.md` §8), на этом этапе
  `detected_datetime` — вход извне, а не результат разбора файла.

Критерий готовности (docs/SPEC.md, критерий §16): 48 тестов pytest
(`pytest -q`) покрывают конфигурацию, расписание, часовой пояс, историю,
защиту от повторной обработки, сопоставление причин и валидацию фото — без
GUI и без браузера. Демонстрационный сценарий `scripts/demo_today.py`
печатает сегодняшние занятия, их состояния и посещаемость на реальных
(вымышленных) примерах из `config/`.

## Этап 3. Планировщик

**Цель:** фоновый `AutomationWorker` (см. ARCHITECTURE.md §2), который сам
по себе ещё не трогает браузер — работает поверх `DemoAdapter`.

- Расчёт времени запуска занятия по правилу расписания, часовому поясу и
  смещению (начало/конец + offset).
- Определение `ПРОПУЩЕНО_ПО_ВРЕМЕНИ`, если приложение не работало в момент
  наступления времени заполнения.
- Обработка занятий по одному, с изоляцией ошибок между независимыми
  занятиями.
- Переходы состояний занятия целиком по схеме §4 ARCHITECTURE.md, включая
  `ЖДЁТ_ДАННЫХ`, `КОНФЛИКТ`, `РЕЗУЛЬТАТ_НЕИЗВЕСТЕН`.

Критерий готовности: тесты планировщика на `DemoAdapter` покрывают —
нормальный проход, нехватку данных, конфликт, неизвестный результат сохранения,
пропуск по времени, изоляцию ошибки одного занятия от других.

## Этап 4. GUI

**Цель:** PySide6-интерфейс поверх уже готовых слоёв данных и планировщика
(на `DemoAdapter`), без блокировки UI-потока.

- Список тренировок дня, статусы занятий (обе оси состояния из §4).
- Ввод/редактирование групп, расписания, папки с фото.
- Ввод отсутствующих, причин, явное подтверждение полноты списка
  отсутствующих.
- Кнопки «Запустить проверочный режим», «Включить автоматический режим»,
  «Запустить вручную».
- Раздел «занятия, ожидающие данных» и «пропущенные по времени».
- Явное отображение ограничения: работает, пока приложение запущено и
  компьютер не спит/на связи.

Критерий готовности: ручная проверка сценария «утро тренера» полностью на
`DemoAdapter`, без блокировки интерфейса во время имитации ожидания/работы
браузера.

## Этап 5. Чтение сайта

**Цель:** изучить реальный сайт журнала (после того как пользователь даст
адрес, доступ и скриншоты/описание процесса) и реализовать в
`PlaywrightRealAdapter` только операции чтения: вход, проверка сессии, поиск
занятия, чтение текущего состояния посещаемости/фото на странице.

- Никаких изменений в журнале на этом этапе.
- Никаких выдуманных селекторов — только то, что подтверждено осмотром
  реального интерфейса.

Критерий готовности: на согласованном тестовом занятии приложение находит
занятие и корректно читает его текущее состояние, не изменяя журнал.

## Этап 6. Запись на сайт

**Цель:** реализовать в `PlaywrightRealAdapter` операции записи: загрузка
фото, простановка посещаемости, комментарии, сохранение и проверка
результата после сохранения.

- Только на явно согласованном с пользователем занятии/тестовой среде.
- Проверочный режим обязателен и не должен писать в журнал (включая поля
  с автосохранением).
- Реализация защиты от дублей и обработки конфликта — на реальном сайте,
  не только в тестах на `DemoAdapter`.

Критерий готовности: на согласованном занятии проверочный режим ничего не
меняет на сайте, а после включения автоматического режима занятие проходит
путь до `СОХРАНЕНО_ПОДТВЕРЖДЕНО` с реальной проверкой результата.

## Этап 7. Комплексная проверка

**Цель:** сквозная проверка нескольких групп/занятий одновременно, включая
крайние случаи из ТЗ.

- Несколько групп с разным расписанием и разными смещениями заполнения.
- Одновременная нехватка данных у одного занятия при нормальной обработке
  остальных.
- Повторный запуск после частичного выполнения и после «неизвестного
  результата».
- Проверка логирования: наличие нужной информации при отсутствии
  персональных данных сверх необходимого.

Критерий готовности: набор сценарных тестов (pytest + `DemoAdapter`, при
возможности — с ограниченной реальной проверкой) проходит без ручного
вмешательства сверх предусмотренных подтверждений.

## Этап 8. Сборка

**Цель:** дистрибутив для Windows, которым может пользоваться тренер без
терминала и без Python.

- PyInstaller (`onedir`), решение по распространению браузерных бинарников
  Playwright (см. открытый вопрос в ARCHITECTURE.md §7).
- Установка/первый запуск без ручного редактирования конфигурационных
  файлов.
- Финальная проверка README/инструкции глазами человека без опыта
  программирования.

Критерий готовности: собранный установщик/дистрибутив запускается на чистой
машине без Python и VS Code, проходит сценарий «утро тренера» в проверочном
режиме.
