# PLAN.md — план разработки по этапам

Восемь этапов. Каждый этап заканчивается коммитом/push и отчётом по схеме:
что готово / как проверено / что осталось / ветка и последний commit.
Реальные изменения в журнале в процессе разработки — только на явно
согласованном с пользователем занятии или в тестовой среде.

## Этап 1. Архитектура (текущий)

**Цель:** зафиксировать архитектуру, сущности, состояния и правила проекта,
не реализуя приложение целиком.

Результат:
- `CLAUDE.md`, `docs/SPEC.md`, `docs/ARCHITECTURE.md`, `docs/PLAN.md`,
  `CURRENT_STATE.md`, `README.md`, `.gitignore`.
- Git подключён к `https://github.com/kuzikovadara58-glitch/my-project.git`,
  ветка `main`.

Как проверено: документы вычитаны на непротиворечивость друг другу и ТЗ;
код не писался, поэтому автоматических тестов на этом этапе нет.

## Этап 2. Данные — ВЫПОЛНЕНО

**Цель:** слой хранения и конфигурации, независимый от GUI и планировщика.

- Зафиксированы версии стека в `requirements.txt` (Python 3.11+, проверено
  на 3.14.6; PySide6, Playwright, PyYAML, python-dotenv, pytest, keyring,
  platformdirs, tzdata) — установлены совместно в чистое окружение, тесты
  прошли. PyInstaller добавится на этапе «Сборка».
- **Отличие от первоначального плана**, зафиксированное здесь, а не молча:
  вместо схемы SQLite для группы/спортсменов/расписания/посещаемости —
  типизированные модели (`journal_automation/config/models.py`), читаемые
  и валидируемые из YAML через `ConfigManager`
  (`journal_automation/config/manager.py`); история выполнения занятий —
  один JSON-файл через `HistoryManager`
  (`journal_automation/services/history_manager.py`), а не таблица SQLite.
  Переход на SQLite откладывается до момента, когда он реально понадобится —
  конкурентный доступ планировщика (этап 3) и GUI (этап 4) к одним и тем же
  данным; до тех пор SQLite был бы неиспользуемой инфраструктурой. Причины
  и последствия — в `docs/ARCHITECTURE.md`, раздел 6.
- Модуль секретов через `keyring` с `.env`-фолбэком только для разработки
  (`journal_automation/secrets.py`), включается явно
  `JOURNAL_ALLOW_DOTENV_SECRETS=1`.
- Единая точка разрешения путей `journal_automation/paths.py` (`AppPaths`):
  каталог пользовательских данных отдельно от каталога с конфигурацией и от
  каталога программы, учитывает будущую сборку в `.exe`.
- Обе оси состояния занятия из `ARCHITECTURE.md` §4 реализованы как
  `TrainingDomainState` и `AutomationState`
  (`journal_automation/domain/states.py`), с таблицей соответствия
  русскоязычному жизненному циклу этапа 1.
- Защита от повторной обработки (`TrainingService.should_process_session`)
  и от перепутывания причины отсутствия между спортсменами
  (`journal_automation/domain/absence.py`, сопоставление по `athlete_id`).
- Доменная модель и проверки фотографии
  (`journal_automation/domain/photo.py`): формат/размер, дубли по хешу
  файла, окно допуска по времени съёмки. Чтение EXIF из реального файла —
  открытый вопрос (см. `docs/ARCHITECTURE.md` §8), на этом этапе
  `detected_datetime` — вход извне, а не результат разбора файла.

Критерий готовности (docs/SPEC.md, критерий §16): 48 тестов pytest
(`pytest -q`) покрывают конфигурацию, расписание, часовой пояс, историю,
защиту от повторной обработки, сопоставление причин и валидацию фото — без
GUI и без браузера. Демонстрационный сценарий `scripts/demo_today.py`
печатает сегодняшние занятия, их состояния и посещаемость на реальных
(вымышленных) примерах из `config/`.

## Этап 3. Планировщик + GUI + безопасный mock-цикл — ВЫПОЛНЕНО

**Отличие от первоначального плана**, зафиксированное здесь, а не молча:
пользователь объединил то, что здесь изначально было отдельными этапами 3
(«Планировщик») и 4 («GUI»), в один этап — desktop-приложение, в котором
планировщик и интерфейс появляются и проверяются вместе, поверх
безопасного mock-адаптера вместо `DemoAdapter`-заглушки без интерфейса.
Ниже — фактический результат; бывший «Этап 4» ниже сужен до того, что
реально осталось несделанным.

- Расчёт момента заполнения занятия по правилу расписания, часовому поясу и
  смещению (начало/конец + offset) —
  `journal_automation/scheduler/timing.py: compute_fill_time`.
- `SchedulerLoop` (`journal_automation/scheduler/core.py`) без зависимости
  от Qt: выбирает ближайшее подходящее занятие, ждёт через
  `threading.Event.wait()` (не занятое ожидание), обрабатывает по одному
  занятию за раз, ошибка одного занятия не прерывает очередь остальных.
  Защита от штормового авто-повтора `ERROR`/`NEEDS_ATTENTION` в рамках
  одного запуска автоматизации — до следующего запуска, не по кругу
  немедленно (см. ARCHITECTURE.md §2, добавление этапа 3).
- `AutomationController` (`journal_automation/scheduler/controller.py`) —
  `QThread`-обёртка: GUI не блокируется, обмен только через Qt-сигналы,
  повторное нажатие «Запустить» не создаёт второй планировщик, остановка —
  кооперативная (не грубое убийство потока), закрытие окна дожидается
  реальной остановки потока (раздел 22).
- `MockJournalAutomation` (`journal_automation/automation/mock.py`) за
  интерфейсом `JournalAutomationPort` — безопасная имитация обработки,
  реальный сайт не затрагивается; поддерживает `--simulate-error` для
  проверки сценария ошибки.
- Desktop-окно на PySide6 (`journal_automation/gui/main_window.py`,
  `main.py`): сегодняшние занятия из `TrainingService.get_sessions_for_today()`,
  обе оси состояния, кнопки «Запустить»/«Остановить», «Последнее событие»,
  минимальный просмотр настроек (timezone/photos/fill_after_start_minutes).
- Демо-режим `python main.py --demo` на полностью изолированных временных
  данных (`journal_automation/demo.py`) — не трогает реальные config/
  данные пользователя; занятия наступают через секунды, а не часы.
- Логирование через `journal_automation/logging_setup.py` (файл + консоль,
  без паролей/фото/лишних персональных данных).
- `HistoryManager` защищён `threading.Lock` — с этого этапа к нему
  обращаются GUI-поток и поток планировщика одновременно.

Критерий готовности (раздел 32 запроса пользователя): `python main.py --demo`
открывает окно, занятия проходят WAITING → RUNNING → SUCCESS (или ERROR при
`--simulate-error`), история сохраняется и переживает "перезапуск"
(docs/PLAN.md проверено тестом `tests/test_duplicate_protection.py`), второе
занятие дожидается своего времени, реальный сайт не затрагивается ни разу.
Автоматизированная проверка (`QT_QPA_PLATFORM=offscreen`, т.к. в среде
разработки нет интерактивного дисплея) подтвердила полный цикл для обоих
демо-занятий и корректную остановку/закрытие без зависших процессов.

## Этап 4. Google Drive Photo Source — ВЫПОЛНЕНО

**Отличие от первоначального плана**, зафиксированное здесь: пользователь
направил этот этап на получение фотографий из Google Drive, а не на
доработку GUI-редактора конфигурации, изначально числившегося тут (см.
«Отложено» ниже) — сохранена нумерация, которую использовал пользователь в
своём запросе.

- `journal_automation/photos/` — новый пакет: `PhotoSource` (Protocol,
  `journal_automation/photos/source.py`) — `PhotoService`
  (`journal_automation/photos/service.py`) не знает деталей Google Drive,
  ровно как `SchedulerLoop` не знает деталей сайта журнала за
  `JournalAutomationPort` (этап 3).
- `GoogleDrivePhotoSource` (`journal_automation/photos/google_drive_source.py`)
  — официальный Google Drive API v3 (не Playwright, не парсинг HTML);
  метаданные запрашиваются отдельно от скачивания, скачивается только узкий
  отобранный набор кандидатов (не вся папка); ограниченный retry с backoff
  для временных ошибок, permission denied — без повтора.
- OAuth 2.0 "installed app" flow для авторизации одного пользователя
  (`journal_automation/photos/google_drive_auth.py`) — пароль от Google
  приложение не получает; `credentials.json`/`token.json` не коммитятся и
  создаются только когда реальная папка действительно настроена.
- Разбор ссылки на постоянную папку Google Drive в `folder_id`
  (`journal_automation/photos/google_drive_url.py`) — поддержаны все
  распространённые форматы ссылок и голый id; ссылка передаётся через
  `config/settings.yaml` (`photos.google_drive.folder_url`), не зашита в
  код. Плейсхолдер (`folder_url: ""`) — ожидаемое состояние: источник фото
  просто отключён, планировщик работает как на этапе 3.
- Приоритет источника времени съёмки: EXIF (`journal_automation/photos/exif_reader.py`,
  через Pillow) → имя файла рекомендованного формата
  (`journal_automation/photos/filename_parser.py`) → метаданные Google Drive
  только если явно разрешено `photos.allow_drive_timestamp_fallback`
  (по умолчанию `false`) — ничего из этого не подделывается ради совпадения.
- Детерминированный выбор лучшего кандидата и явная неоднозначность
  (`PhotoSelectionStatus.AMBIGUOUS`) вместо случайного выбора
  (`journal_automation/photos/service.py: _select_best`).
- `WAITING_FOR_PHOTO` до дедлайна (`photos.wait_for_photo_until_minutes_after_end`)
  и `NEEDS_ATTENTION` после — доменное правило «нет валидного фото → нет
  финального заполнения журнала» реализовано в `SchedulerLoop`, применится
  одинаково и для будущего реального адаптера сайта.
- Локальный кэш скачанных фото отдельно от постоянных данных
  (`journal_automation/photos/cache.py: PhotoCache`), с очисткой по
  `cache_retention_days` и защитой файлов, которые сейчас используются.
- GUI: статус «Фото: ...» на каждое занятие и кнопка «🔄 Проверить фото»
  (`PhotoCheckWorker` — отдельный `QThread`, не блокирует интерфейс).
- Demo-режим (`FakeGoogleDrivePhotoSource`) не обращается к реальному Google
  Drive; поддержаны `--simulate-photo-missing`, `--simulate-drive-error`,
  `--simulate-photo-ambiguous`.

Критерий готовности (раздел 44 запроса пользователя): все пять состояний
(`FOUND`, `WAITING_FOR_PHOTO`, `NOT_FOUND`, `SOURCE_UNAVAILABLE`,
`AMBIGUOUS`) реализованы и покрыты тестами; демонстрационные сценарии
проходят полный конвейер `TrainingSession → PhotoService →
GoogleDrivePhotoSource → отбор кандидатов → скачивание → EXIF/имя файла →
локальный временный путь → MockJournalAutomation` без обращения к реальному
Google Drive.

### Отложено (без номера этапа): GUI — расширенный редактор конфигурации

Было изначально запланировано как «Этап 4» до того, как пользователь направил

- Раздел «занятия, ожидающие данных» и «пропущенные по времени» как

## Этап 5. Чтение сайта

**Цель:** изучить реальный сайт журнала (после того как пользователь даст
адрес, доступ и скриншоты/описание процесса) и реализовать в
`PlaywrightRealAdapter` только операции чтения: вход, проверка сессии, поиск
занятия, чтение текущего состояния посещаемости/фото на странице.

- Никаких изменений в журнале на этом этапе.
- Никаких выдуманных селекторов — только то, что подтверждено осмотром
  реального интерфейса.

Критерий готовности: на согласованном тестовом занятии приложение находит
занятие и корректно читает его текущее состояние, не изменяя журнал.

## Этап 6. Запись на сайт

**Цель:** реализовать в `PlaywrightRealAdapter` операции записи: загрузка
фото, простановка посещаемости, комментарии, сохранение и проверка
результата после сохранения.

- Только на явно согласованном с пользователем занятии/тестовой среде.
- Проверочный режим обязателен и не должен писать в журнал (включая поля
  с автосохранением).
- Реализация защиты от дублей и обработки конфликта — на реальном сайте,
  не только в тестах на `DemoAdapter`.

Критерий готовности: на согласованном занятии проверочный режим ничего не
меняет на сайте, а после включения автоматического режима занятие проходит
путь до `СОХРАНЕНО_ПОДТВЕРЖДЕНО` с реальной проверкой результата.

## Этап 7. Комплексная проверка

**Цель:** сквозная проверка нескольких групп/занятий одновременно, включая
крайние случаи из ТЗ.

- Несколько групп с разным расписанием и разными смещениями заполнения.
- Одновременная нехватка данных у одного занятия при нормальной обработке
  остальных.
- Повторный запуск после частичного выполнения и после «неизвестного
  результата».
- Проверка логирования: наличие нужной информации при отсутствии
  персональных данных сверх необходимого.

Критерий готовности: набор сценарных тестов (pytest + `DemoAdapter`, при
возможности — с ограниченной реальной проверкой) проходит без ручного
вмешательства сверх предусмотренных подтверждений.

## Этап 8. Сборка

**Цель:** дистрибутив для Windows, которым может пользоваться тренер без
терминала и без Python.

- PyInstaller (`onedir`), решение по распространению браузерных бинарников
  Playwright (см. открытый вопрос в ARCHITECTURE.md §7).
- Установка/первый запуск без ручного редактирования конфигурационных
  файлов.
- Финальная проверка README/инструкции глазами человека без опыта
  программирования.

Критерий готовности: собранный установщик/дистрибутив запускается на чистой
машине без Python и VS Code, проходит сценарий «утро тренера» в проверочном
режиме.
