# ARCHITECTURE.md — архитектура проекта

Статус: подготовительный этап (архитектура). Реальный сайт журнала ещё не
изучен — везде, где это влияет на решение, явно указано «открытый вопрос».

## 1. Слои системы

Пять независимых слоёв, как того требует [CLAUDE.md](../CLAUDE.md):

```
┌─────────────────────────────────────────────────────────────┐
│  GUI (PySide6)                                               │
│  — отображает группы, занятия, статусы, очередь ожидания     │
│  — только читает состояние и отправляет команды пользователя │
│  — никогда не вызывает Playwright напрямую                   │
└───────────────────────────┬───────────────────────────────────┘
                             │ Qt-сигналы / команды (потокобезопасно)
┌───────────────────────────▼───────────────────────────────────┐
│  Планировщик (Scheduler, отдельный поток)                     │
│  — следит за временем, часовыми поясами, сменой дня            │
│  — решает, какое занятие уже можно обрабатывать                │
│  — вызывает бизнес-логику по одному занятию за раз,            │
│    ошибка одного занятия не останавливает очередь              │
└───────────────────────────┬───────────────────────────────────┘
                             │ вызовы в процессе (тот же поток)
┌───────────────────────────▼───────────────────────────────────┐
│  Бизнес-логика (JournalService)                                │
│  — состояние занятия, проверки полноты данных, dry-run/авто    │
│  — сопоставление спортсменов, шаблоны причин, защита от дублей │
│  — не знает про Qt и не знает про конкретный сайт               │
└───────┬───────────────────────────────────────────┬───────────┘
        │                                            │
┌───────▼─────────────────┐              ┌───────────▼───────────┐
│ Хранилище данных          │              │ Адаптер сайта          │
│ (SQLite + файлы + keyring)│              │ (JournalAdapter)       │
│ — группы, расписание,     │              │ — Demo / Playwright    │
│   занятия, посещаемость,  │              │ — login/поиск занятия/ │
│   журнал действий          │              │   фото/посещаемость/  │
│                            │              │   сохранение/проверка │
└────────────────────────────┘              └────────────────────────┘
```

Правило зависимостей: GUI зависит от бизнес-логики через тонкий интерфейс
команд/сигналов; бизнес-логика не зависит ни от GUI, ни от конкретной
реализации адаптера сайта (зависит только от интерфейса `JournalAdapter`).

## 2. Модель совместной работы GUI, планировщика и браузера

**Решение:** планировщик и вся работа с Playwright выполняются в одном
выделенном фоновом `QThread` («AutomationWorker»), который живёт всё время
работы приложения. GUI-поток никогда не блокируется ожиданием времени
тренировки или ответом браузера.

Почему так, а не отдельный процесс (`multiprocessing`/`QProcess`):

- Playwright уже запускает браузер как отдельный внешний процесс — это даёт
  часть изоляции «бесплатно»: падение вкладки браузера не роняет Python.
- Синхронный API Playwright достаточно вызывать из одного выделенного потока,
  не трогая объекты Qt напрямую — тогда поток GUI не блокируется, а поток
  автоматизации не обязан быть async.
- Межпроцессное взаимодействие (IPC, сериализация команд, перезапуск при
  падении процесса) — заметно больше сложности для первой версии без явной
  необходимости. Если на этапе «Запись на сайт» выяснится, что стабильность
  требует отдельного процесса — это будет пересмотрено и явно отмечено в
  `CURRENT_STATE.md`.

Правила взаимодействия:

- GUI → Worker: только через потокобезопасные команды (Qt `Signal`/`Slot`
  с `Qt.QueuedConnection`), например «включить автоматизацию», «запустить
  занятие X в проверочном режиме», «подтвердить полноту посещаемости».
- Worker → GUI: только через сигналы с готовыми данными (например,
  `occurrence_state_changed(occurrence_id)`), GUI перечитывает нужную строку
  из хранилища и обновляет отображение. GUI никогда сам не пишет в БД
  состояние занятия, которое меняет Worker.
- Единственный писатель в SQLite для состояния занятий и результатов —
  Worker/бизнес-логика. GUI пишет только пользовательский ввод (группы,
  расписание, отсутствующие, причины, подтверждения) — тоже через
  бизнес-логику, а не напрямую в БД, чтобы проверки полноты данных не
  дублировались в двух местах.
- Внутри Worker обработка занятий идёт последовательно, но по одному
  занятию за раз и с изоляцией ошибок: исключение при обработке одного
  занятия переводит его в статус `ERROR` и не прерывает очередь остальных
  независимых занятий (см. §4).

## 3. Сущности

### Группа (Group)
`id`, `name`, состав спортсменов, ссылка на правило расписания.

### Спортсмен (Athlete)
`id` (локальный), `site_id` (nullable — id на сайте журнала, если есть),
`full_name` (ФИО), `gender` (для согласования «отпросился»/«отпросилась»),
`group_id`.

### Правило расписания (ScheduleRule)
`group_id`, дни недели, время начала/окончания, `timezone` (по умолчанию
`Europe/Moscow`), смещение заполнения (после начала N минут / после конца
N минут, по умолчанию — конец + 10 минут).

### Занятие (Occurrence)
Конкретный экземпляр тренировки на конкретную дату, порождённый из
`ScheduleRule`. Центральная сущность для защиты от дублей и от неизвестного
результата. Состояния — см. §4.

### Фотография (Photo)
`occurrence_id`, путь к файлу, заявленное время съёмки (из EXIF, если есть),
статус проверки (`ожидает`, `нужно подтверждение`, `подтверждено`),
контрольная сумма файла (для защиты от повторной загрузки).

### Запись посещаемости (AttendanceRecord)
`occurrence_id`, `athlete_id`, статус (`присутствовал` / `отсутствовал`),
причина (шаблон или свой текст), состояние подтверждения списка
отсутствующих на уровне занятия — см. §4.

### Шаблон причины (AbsenceReasonTemplate)
`id`, текст в мужском роде, текст в женском роде, разрешён ли свой текст.

### Адаптер сайта (JournalAdapter)
Интерфейс, не сущность данных — см. §5.

### Журнал действий (ActionLogEntry)
`occurrence_id`, `timestamp`, этап, результат, описание ошибки (без
персональных данных сверх необходимого).

## 4. Состояния занятия (Occurrence)

Занятие проходит через две независимые оси состояния: **готовность данных**
и **статус обработки**. Их нельзя схлопывать в одну — нехватка данных не то
же самое, что ошибка обработки, а обработка не должна начинаться, пока
данные не готовы.

### 4.1 Готовность данных (проверяется независимо по каждому пункту)

| Аспект | Возможные состояния |
|---|---|
| Фото | `нет фото` → `есть фото, нужно подтверждение` → `подтверждено` |
| Посещаемость | `нет данных` → `есть список отсутствующих, не подтверждён` → `подтверждено (список полный)` |
| Причины | для каждого отсутствующего: `не указана` → `указана` |

Занятие считается **готовым к обработке**, только когда: фото подтверждено
(или явно решено обрабатывать без фото — открытый вопрос UX, см. §8), список
отсутствующих подтверждён как полный, и у каждого отсутствующего есть причина
(или пустой комментарий явно допустим для сайта).

### 4.2 Статус обработки (жизненный цикл занятия)

```
СОЗДАНО (из расписания)
   │
   ▼
ОЖИДАНИЕ_ВРЕМЕНИ ──(время наступило, компьютер был включён)──▶ ГОТОВО_К_ЗАПУСКУ
   │
   └─(время наступило, но приложение не запускалось — комп. был выключен)
                                                    ▼
                                          ПРОПУЩЕНО_ПО_ВРЕМЕНИ (не заполняется
                                          автоматически задним числом, видно
                                          пользователю отдельным списком)

ГОТОВО_К_ЗАПУСКУ ──(данные не готовы, см. 4.1)──▶ ЖДЁТ_ДАННЫХ (не блокирует
                                                    другие занятия)
ГОТОВО_К_ЗАПУСКУ ──(данные готовы, режим = проверочный)──▶ ПРЕДПРОСМОТРЕНО
                                                            (журнал не изменён)
ГОТОВО_К_ЗАПУСКУ ──(данные готовы, режим = автоматический)──▶ В_ОБРАБОТКЕ
ЖДЁТ_ДАННЫХ ──(данные донесены и подтверждены)──▶ ГОТОВО_К_ЗАПУСКУ

В_ОБРАБОТКЕ ──(вход/навигация/загрузка фото/простановка посещаемости)──┐
                                                                        ▼
                                                          ОТПРАВЛЕНО_НА_СОХРАНЕНИЕ
                                                                        │
                              ┌─────────────────────────────────────────┤
                              ▼                                         ▼
                     СОХРАНЕНО_ПОДТВЕРЖДЕНО                 РЕЗУЛЬТАТ_НЕИЗВЕСТЕН
                     (проверка после сохранения               (потеря связи и т.п. —
                      прошла успешно)                          требует явной проверки
                                                                перед повтором, не
                                                                автоматического повтора)

В_ОБРАБОТКЕ / ОТПРАВЛЕНО_НА_СОХРАНЕНИЕ ──(данные на сайте отличаются
                                            от подготовленных)──▶ КОНФЛИКТ
                                            (не перезаписывается автоматически)

В_ОБРАБОТКЕ ──(элемент интерфейса сайта не найден/сайт изменился)──▶ ОШИБКА
В_ОБРАБОТКЕ ──(тренировка отменена/перенесена)──▶ ОТМЕНЕНО
```

Ключевые инварианты:

- Переход в `В_ОБРАБОТКЕ` возможен только из `ГОТОВО_К_ЗАПУСКУ` и только
  когда данные прошли проверку готовности (§4.1) — иначе занятие остаётся в
  `ЖДЁТ_ДАННЫХ` сколько угодно долго, не влияя на остальные.
- `РЕЗУЛЬТАТ_НЕИЗВЕСТЕН` — терминальное состояние без автоматического
  повтора. Повтор возможен только после явной проверки фактического
  состояния занятия на сайте (человеком или отдельной сверкой при следующем
  запуске приложения).
- `КОНФЛИКТ` и `ОШИБКА` не блокируют обработку других занятий — изоляция
  ошибок на уровне одного занятия (см. §2).
- Один `Occurrence` = одна попытка привязки фото/посещаемости на сайте;
  повторный запуск того же занятия сначала проверяет текущее состояние на
  сайте (по устойчивому идентификатору занятия, не по факту нажатия кнопки в
  прошлый раз) и продолжает с нужного шага, а не начинает заново — это и
  есть защита от дублей и от частичного выполнения.

## 5. Адаптер сайта (JournalAdapter)

Абстрактный интерфейс, скрывающий конкретный сайт от бизнес-логики:

- `login(credentials) -> LoginResult`
- `is_session_valid() -> bool`
- `find_occurrence(group, date, time_window) -> RemoteOccurrenceRef | NotFound`
- `get_current_state(ref) -> RemoteOccurrenceState` (для обнаружения конфликтов
  и для продолжения с нужного шага при повторном запуске)
- `attach_photo(ref, photo) -> Result`
- `set_attendance(ref, attendance) -> Result`
- `set_comment(ref, athlete, text) -> Result`
- `save(ref) -> Result`
- `verify_saved(ref) -> VerificationResult`

Реализации:

- **DemoAdapter** — используется до изучения реального сайта и в тестах.
  Имитирует сайт в памяти/на локальной HTML-заглушке, позволяет
  воспроизводить конфликты, «неизвестный результат» и ошибки для проверки
  логики без реального журнала.
- **PlaywrightRealAdapter** — появится на этапах «Чтение сайта» / «Запись на
  сайт», после того как пользователь предоставит реальный адрес сайта и
  скриншоты/описание процесса. До этого момента реальные селекторы и адреса
  страниц не придумываются.

## 6. Хранение данных

- **SQLite** — единственный источник истины во время работы приложения:
  группы, спортсмены, расписание, занятия и их состояния, посещаемость,
  журнал действий. Путь к БД — в пользовательском каталоге данных (например,
  через `platformdirs`), не рядом с установленной программой (открытый
  вопрос: точный путь — `%LOCALAPPDATA%\<AppName>` или `%APPDATA%\<AppName>`,
  решается на этапе «Данные»).
- **Файлы фотографий** — читаются из папки, указанной пользователем; в
  первой версии не обязательно копируются в каталог данных приложения (само
  копирование — открытый вопрос UX/хранилища, см. §8).
- **YAML** — только формат импорта/экспорта настроек (группы, расписание,
  шаблоны причин) для резервного копирования и переноса, а не альтернативный
  источник истины во время работы — иначе GUI и YAML разойдутся между собой.
- **Секреты** (логин/пароль от журнала) — через `keyring` (Windows Credential
  Manager backend), никогда не в SQLite и не в YAML.
- **Логи** — через стандартный `logging`, отдельно от каталога данных,
  ротация по размеру/времени; без паролей, фотографий и лишних персональных
  данных (см. правило 15 в [CLAUDE.md](../CLAUDE.md)).

## 7. Сборка

- PyInstaller, режим `onedir` для Windows (проще диагностировать проблемы
  запуска у пользователя, чем `onefile`).
- Playwright требует отдельно установленных бинарников браузера
  (`playwright install chromium`) — конечный пользователь не должен делать
  это через терминал. Открытый вопрос для этапа «Сборка»: либо (а)
  встраивать бинарники браузера в дистрибутив, либо (б) при первом запуске
  GUI сам скачивает браузер с прогресс-баром, без участия пользователя в
  терминале. Решение принимается на этапе «Сборка» после оценки размера
  дистрибутива.

## 8. Открытые вопросы (не решать, пока нет данных от пользователя)

- Реальный адрес сайта, его страницы и селекторы — нужны скриншоты/описание
  процесса от пользователя.
- Точные версии Python/PySide6/Playwright/PyInstaller — фиксируются на этапе
  «Данные» после проверки совместимости, не сейчас.
- Нужно ли копировать фотографии в каталог данных приложения или работать
  с ними по месту — решается при проектировании модуля фото на этапе
  «Данные»/«Запись на сайт».
- Поведение, если фото для занятия так и не появилось к моменту дедлайна —
  занятие остаётся «Ожидает фото» бессрочно или есть отдельный порог показа
  как «просрочено» — уточнить у пользователя при проектировании GUI.
